# H2O .ui 静态解析突破（2026-11-05）

> 承接 docs/H2O_UI系统逆向分析.md §三（未解项）。本轮用纯静态反汇编（capstone + NSO 重定位解析）
> 回答了三个遗留问题中的两个半，并拿到一个**裁决性结论**：**HUD 位置坐标不在 .ui 文件里**。
> 由此「改文件移位」（FS overlay 字节补丁）对移位需求是死路，主线确认走运行时写值。

## 一、裁决性结论：位置不在资源文件里（本轮最重要）

对全部 397 个 .ui 做全文件 float 对扫描（值域 (2,1280]×(2,720]，排除 0/1 干扰）：

- **ConsoleHUD.ui：0 命中**（一个位置对都没有）
- 全库仅 123 命中，且全是字体度量类反复值（55.85/58.85/194.23/917.85 等，见 BattleNet*/Console* 文本面板）
- 值区里存在的浮点只有锚点/缩放常量（`00 00 80 3F` = 1.0f 等）

⇒ **节点位置是运行时锚定+父相对计算出来的**，文件里只有锚点语义、没有绝对坐标。
⇒ 推论：
1. **移位 = 只能运行时写节点对象的计算后位置**（hle_hudmove 路线确认，没有替代）。
2. FS overlay 资源劫持（hle_fs.c DM_ROMFS_OVERLAY）仍可用，但只适用于**文件里确实存了的东西**
   （字符串文本、贴图引用、模板结构、锚点常量），对"挪血球/小地图"无效。
3. 原计划「等 1-3GB hud-dump 再离线找位置字段」不变是主线，但**dump 内容可以砍到 MB 级**（见 §四）。

## 二、加载链全貌（本轮反汇编实证，全部地址可复现）

### 2.1 双解析家族（都汇入 0x4AE400 构建）

```
家族 A（内存缓冲版）:
  0xb342c → 0x74C470(buf1,len1,w2,w3=1,x4,w5=buf2,w6) → 0x4AE810 ×2（主数据+第二缓冲）
  0x4AE810(buf,len,w2,type=0xC,x4,&out,0x3E8):
    new 0x1078 状态机 → 0x763b60(vptr=[0x1159518]+0x10) → 0x763C00(存参)
    → vcall [vptr+0x18] → x23=state[0x28] → [x23+0x1064]=type → 0x4AE400(x23) → *out=x23

家族 B（按名版，游戏资源真正走这条）:
  0x7660a0 LoadResource(name, &out):  0x4ADE00(name,0,0,0,&out,0x3E8)
  0x4ADE00: 互斥 0x1900d88 + 去重链表（strcmp 名字匹配，bit6=重载）
    → new 0x1070 → 0x763990(init) → 0x763a30(obj,name,w2,w3,w4):
        strncpy(obj+0x64, name, 0xfff)   ← 0xc70ce0 = strncpy（PLT，重定位实证）
        obj+0x1064=w2, obj+0x1068=w3
    → vcall [vptr+0x18] = 0x763ad0:
        new 0x10c8 解析对象 → 0x760610(obj, name=state+0x64, &state+0xb8, 0, w1064, w1068, 1)
        → 0x760740 分块流式解析（块大小 obj+0x1038，异步流 obj+0x1050）
```

### 2.2 位流容器（A1B2C3D4）头解析器 0x7611b0 —— 这是另一种容器，不是 .ui 本体

```
首块头校验:  u32@0x00 == 0xD4C3B2A1 → 大端变体：全头 rev 字节反转后解析
             u32@0x00 == 0xA1B2C3D4 → 直接解析（小端）
             都不是 → 错误码 5（对应 0x4AE810 里 state+0x14==5 特殊路径）
头字段映射（解析对象 0x10c8）:
  @0x10 → +0x1008（flags，bit3 测试）;  @0x14 → +0x1060（元素数）
  @0x20/0x24/0x28/0x2c → +0x1070/74/78/7c（四个位宽/参数，全元素统一）
  @0x08(u64) → +0x1018;  @0x30/34 → +0x1080/84;  @0x38 → +0x1020;  @0x3c → +0x1038(块大小)
```

**注意**：此前进度文档把「位宽是文件头透传」安在 .ui 头 @0x20 上——实际这个映射属于
A1B2C3D4 位流容器（其 @0x20 才是位宽），**.ui 的 DEADBEEF 头不走这个解析器**。

### 2.3 .ui（DEADBEEF）的真校验点

```
0x7477d8: 读 16 字节 → cmp 0xDEADBEEF → 命中 → vcall [[[0x1159188]]→vt+0xC0](mgr, res, &hdr16, &hdr16, str)
0x747570: 构造 {0xDEADBEEF, u32, u32, u32} 头（写侧/内存组头）
0xbd7760: *x0 = 0xDEADBEEF 单行助手
0x51d1ec: 0xDEADBEEF 作为哈希种子传入 0xa482e0（结果只是存常量对 {seed, 0x29a}，非哈希）
[0x1159188] 重定位链: 0x1159188 → 0x10cb788 → 0x1a21648（BSS，运行时构造的对象）
```

## 三、.ui 文件结构新增结论

1. **头区 @0x20 三元组 {count, size, off} 实测**（ConsoleHUD: 66/184/0x5EE0）：
   `off+size == 0x5F98 == 字符串表区起点` 精确吻合——即 @0x24/@0x28 描述「字符串表前的
   184 字节区」，该区**全零**（语义未明：可能补丁区/运行时填充区）。@0x20 的 66 语义未定。
2. **目录表 @0xD0**（每条 {u64 hash, u32 off, u32 cnt}）：
   - off 指向字符串表：表 1 带 16 字节零头再接串，表 2 直接接串（ConsoleHUD 实证）。
   - 哈希算法仍未破解（FNV-1a/1-64 对内容均不中）。
3. **payload = {u64 hash, u32 off, u32 len} 条目流**（16 字节对齐散布，条目间零填充）：
   - off 为**池基址（0x5f98）相对偏移**（实测 entry@0x240 off=0x6080 → 0xC018 值区）。
   - 指向两类目标：值区数据（含 1.0f 锚点常量、-1、小整数表）与字符串切片
     （{u64 0x10, u32 off, u32 len} 形态的池内切片，字符串 = off+0x10 起 len 字节）。
   - 值区 ≈ 0xC000–0xEBxx。条目散布的编组方式（@0x238 处 u32 9 = 组计数？）未完全解开。
4. **锚串实测**（ConsoleHUD 池内）：`Wizard_Male`、`ConsoleHUD_main.LayoutRoot.AvengerKillsTemplate.PlayerPortraits`、
   `$anon$Wizard_Male`、`UI:Portrait_Wizard_Male`、`CoOpLootAnimP2`、`ConsoleHUD_main`、
   `$anon$CoOpLoo…`、`SansSerif`、`name`（属性名明文！）、`hp_bar_template_player`（跨条目拼接）。

## 四、0x4AE400 构建器全解（本轮最重要静态成果）

```
0x4AE400(layout):
  1. 按 +0x1064(type) 升序把 layout 插入全局有序链表（0x1900d88+0xe8，0x1900d40 管理器域）
  2. count = layout[+0x1060]（元素数）
  3. new count×0x28 记录数组 → layout[+0x1058]（挂数组基址，0x28 字节/元素确认）
  4. 逐元素循环:
       0x761940(layout, i, out24)          # 访问器读位流元素
       rec[i] = {layout, out24[0x08], out24[0x10], out24[0x18], 0}   # 三个 u64
       h   = out24[0x08]                   # 元素 ID = 位流首字段（64 位）
       bucket = FNV1a32(h 低 32 字节) & mask   # 0x811C9DC5 / 0x01000193，逐字节
       插入全局哈希表 0x1900F20: {next, key=h(u64), val=&rec[i]}
       key 已存在 → 走 0x4ae6b8 共享/去重路径（跨布局同名元素共享记录）
```

**意义**：
- 0x1900F20 表 = **元素 ID → 记录** 的运行时查找原语。宿主可直接遍历该表，
  过滤 `rec.layout == ConsoleHUD布局`，得到该布局全部元素的 {ID, B, C} —— 不需要任何内存扫描。
- 元素 ID（位流首 64 位字段）是节点身份哈希。**拿到运行时 key 集合后，离线对 .ui 池内
  已知节点路径跑哈希候选（FNV-1a-64 等），命中即破解 ID 算法** → 得到「按名字找元素」闭环。
- 记录里只有 3 个 u64 ID，**没有坐标**——再次印证位置在运行时节点对象里。

## 七、证伪记录（勿重走）

- 0xc70ce0 不是头部变换/解密——是 strncpy（拷资源名）。「.ui 头被解密成 A1B2C3D4」假设否。
- .ui+0x1E0 处没有第二层 A1B2C3D4 头（实测全零 + @0x238 小整数）。
- 0xa482e0 不是哈希函数（只是存 {w1, 0x29a} 常量对）。
- 「.ui 头 @0x20 三元组 = 位宽」是把 A1B2C3D4 容器的字段映射错安到 .ui 头上（§2.2 澄清）。
